一、实验概况

1.1 实验名称

Riffoid IR Compiler与IR Plugin Browser Runtime黑盒集成验证（Riffoid_BlackBox_Test_01）

1.2 实验目的

本次实验旨在通过自然语言业务需求，验证新版sim_engine_compiler与Riffoid IR Plugin之间的实际集成情况。

实验不直接向Pi Web提供Business IR Schema或Plan字段定义，而是以普通业务需求作为输入，要求Pi Web通过插件正常工作流程完成模型构建、检查、编译和仿真。

重点验证以下内容：

  1. Pi Web是否能够根据自然语言需求构建符合要求的Business IR。
  2. Compiler是否能够生成新版融合可靠性结构（Fused Reliability Plan）。
  3. IR Plugin是否能够正确接收并保存Compiler生成的Plan。
  4. Browser Runtime是否能够执行新版Fused Plan。
  5. Runtime是否能够正确处理实例级故障、冗余逻辑和维修。
  6. 实际仿真结果是否符合预期的可靠性语义。

二、实验业务需求

本次采用的业务需求为：

一架F35战斗机执行一个飞行任务，配备一套由两个功能相同、能够独立工作的雷达单元组成的雷达设备。

雷达系统采用1-out-of-2冗余机制：

  • 两个雷达单元中至少有一个正常，整个雷达系统就可以继续工作。
  • 两个雷达单元全部发生故障，整个雷达系统才失效。
  • 每个雷达单元的故障率为每飞行小时0.5。
  • 每个雷达单元发生故障后的维修时间为10分钟。

本次实验的主要可靠性配置：

雷达组件组radar-system
冗余类型k_out_of_n
k1
n2
雷达实例数量2
实例 Aradar-a
实例 Bradar-b
单实例故障率0.5 / 飞行小时
单实例维修时间10 分钟

对于需求中未明确指定的部分，模型采用了默认配置，并在原始需求记录中进行了说明。

三、实验执行过程

3.1 自然语言需求转换为Business IR

通过Pi Web对话输入业务需求，要求插件按照正常工作流程创建模型。

实际完成：

  • 创建原始需求记录。
  • 根据业务需求生成Business IR。
  • 将Business IR写入插件工作区。
  • 使用project_ir_check执行检查和Seal。

第一次Check / Seal成功，但第一次Compile出现：

invalid_ir @ business.fingerprint checksum mismatch

经调查，问题与浮点数1.0在Python canonical JSON和JavaScript JSON序列化时的表示差异有关。将successPoint: 1.0修正为整数1后，重新执行Check / Seal和Compile，最终成功。

该问题及修正过程被保留在实验记录中。

五、实验验证结论

5.1 Compiler集成验证

本次实验实际证明：

  1. Pi Web能够根据自然语言业务需求创建Business IR。
  2. Business IR能够通过插件的Check / Seal流程。
  3. 新版Compiler能够生成 aircraft-support-plan/v1alpha2 Fused Plan。
  4. Fused Plan中能够正确生成component groups和component instances。
  5. 编译生成的Plan能够通过插件流程传递到Browser Artifact。
  6. 插件交接过程中，Plan指纹与编译记录保持一致。

5.2 Browser Runtime集成验证

本次实验实际证明：

  1. Browser Runtime 0.4.0能够加载并执行新版Fused Plan。
  2. Runtime能够识别实例级可靠性结构。
  3. Runtime能够分别维护radar-a和radar-b的可靠性状态。
  4. 单个实例故障不会直接导致整个系统失效。
  5. 两个实例全部故障后能够触发系统失效。
  6. Runtime能够执行实例级维修。
  7. 仿真能够正常生成Run Result，并通过插件的project_ir_result获取结果。

5.3 最终结论

本次黑盒实验达到了预定目标。

新版sim_engine_compiler与Riffoid IR Plugin的核心集成链路已经通过实际端到端实验验证：

自然语言需求
→ Business IR
→ Check / Seal
→ Compiler
→ Core IR
→ Fused Plan
→ Browser Artifact
→ Browser Runtime
→ Run Result

同时，针对提出的实例级冗余语义，本次实验已经实际验证：

  • 不同组件组之间的可靠性逻辑按各自定义执行。
  • 同一组件组内采用k-out-of-n冗余。
  • quantity不等同于冗余。
  • 单实例故障不会导致整个系统失效（当剩余健康实例满足k时）。
  • 全部必要实例失效后，系统正确进入失效状态。
  • 故障和维修能够落实到具体实例。

因此，本次实验不仅验证了Plan的生成和传递，也验证了Fused Plan在Browser Runtime中的实际执行行为。

六、实验边界及注意事项

本次实验成功不代表所有功能和所有执行环境都已完成验证。

仍需明确以下边界：

  1. 本次只验证了F35雷达组件的1-out-of-2场景，不代表所有复杂组件树、父子实例映射和多层冗余组合都已完成验证。
  2. 本次使用Browser Runtime 0.4.0，执行位置为user-browser，执行等级为local-unverified。实验结果证明本地浏览器执行链路可用，但不代表已经完成外部可信执行环境验证。
  3. 本次没有验证Rust AOT Compiler与插件Browser Runtime的直接集成。
  4. 本次没有验证所有历史legacy Plan的迁移和兼容行为。
  5. 首次Compile出现的fingerprint checksum mismatch已通过将successPoint从浮点数1.0改为整数1解决，该问题应保留为本次实验中的序列化兼容性记录。
  6. 部分统计指标存在不同事件分支的计数口径差异。例如单实例故障后成功返场的运行中，completed_sorties为0，但successful_mission_waves为1。评估任务结果时应结合事件流和成功判定指标，而不是单独依赖某个计数。
  7. 双实例故障运行结束时，两个实例的终态快照均显示failed:false，是因为仿真结束前已经完成维修。故障是否发生应依据事件流及故障指标判断，而不能只看终态快照。
